# Project: PMAFI Website

**What this is:** The official website of the Philippine Military Academy Foundation, Inc. (PMAFI) — a non-stock, non-profit foundation supporting PMA.

**Live URL:** https://www.pmafi.org  
**Stack:** Next.js 16 · React 19 · Tailwind CSS v4 · Framer Motion 12 · TypeScript · shadcn/ui · Vercel

## Key facts for agents

- All pages are in `src/app/` using the App Router. Section components live in `src/components/sections/`, one subfolder per page.
- **Every dark page hero is `src/components/ui/PageHero.tsx`.** Do not hand-roll another one — this markup was copy-pasted across seven pages and drifted into a dozen blob sizes and two padding scales before it was extracted. Pass `eyebrow`, `title` (with the accent word in `<span className="text-gold-shimmer">`), `lede`, and optional `children` for a CTA. The home page's `sections/Hero.tsx` is deliberately separate — it is a full-viewport hero, not a page header.
- **Section vertical rhythm is a three-step scale: `py-16` (compact) · `py-20` (standard) · `py-24` (generous).** Nothing else. Reach for one of these rather than inventing a `py-28`. **The one exception is navbar clearance, which is not rhythm**: the navbar is `fixed` and transparent, so nothing in the layout reserves space for it and the top padding of a full-height hero is the only thing that keeps content out from under it. `Hero.tsx` carries `py-32` and `PageHero.tsx` `pt-28` for that reason alone, and both are sized against the bar (96px on mobile, 104px from `sm`) rather than against this scale. Anything that makes the bar taller — a larger seal, another line of brand text — has to be re-checked against both, on a short viewport where the hero content overflows rather than a desktop one where it never reaches the top.
- **`STATUS.md` is the source of truth for what is and isn't working** — pages, verified flows, configuration, open issues, and what is blocked on PMAFI. It is committed. `BUILD-STATUS.md` holds only engagement and payment matters and is **excluded from git** (`.git/info/exclude`) because this repository is public; never commit it. The scope docs (`PHASE-1/2/3-SCOPE.md`) describe what was sold, not what is live. `references/pmafi-information-request.md` lists everything still outstanding from the client.
- The **Board of Trustees** is a section of `/about` (`src/components/sections/about/BoardOfTrustees.tsx`), not its own page. Its `id="board"` anchor is load-bearing — nav, footer, programs page and the FAQ assistant all link to `/about#board`, and `/board` 308-redirects there via `next.config.ts`.
- **Fund names have one canonical list: `src/lib/funds.ts`.** The name is typed by hand into two separate sheets — the donation log's Fund column and the Fund Updates tab's — and `/donate/status` joins a donor's gift to their fund's updates by matching those strings, so both parsers read through `canonicalFund()`. The authority is the PMAFI brochure, which offers exactly two funds (Professorial Chair Fund, ₱250,000 minimum; Endowment Fund, ₱100,000); `General Fund` is ours for undesignated gifts. **"Facilities & Modernization" is a programme area, not a fund** — it appears on `/programs`, `Services.tsx` and `SupportImpact.tsx`, and adding it back to the fund list would advertise an offer PMAFI has never made. An unrecognised fund is passed through trimmed rather than dropped, so a fund opened later still works provided both sheets spell it identically. `references/donations-sheet.gs` mints references and must stay in step with this list.
- The **donor giving lookup** at `/donate/status` requires email **plus** a reference code, unlike the membership check which needs only an email. That asymmetry is deliberate: it exposes amounts rather than a standing. Every failed lookup must keep returning one identical message — distinguishing "no such reference" from "wrong email" would turn the page into an oracle for whether an address has ever donated.
- The site uses **Tailwind CSS v4** — the config is in `src/app/globals.css` (not `tailwind.config.js`). Custom animations (`animate-drift`, `animate-drift-slow`, `animate-ember`) are defined there.
- **Brand gold has two tokens** (defined in `globals.css` `@theme`): `text-gold` (`#C8A951`, vivid — use on dark/navy backgrounds) and `text-gold-ink` (`#8A6A22`, darker — use for small text on light/white backgrounds). The vivid gold fails WCAG AA contrast on light backgrounds, so always use `text-gold-ink` for gold text on white/slate sections. Likewise, muted helper text on light backgrounds must be `text-slate-500`+ (not `text-slate-400`, which fails AA). All public pages currently score 100 on Lighthouse accessibility — keep it that way. **The gold button's hover shade is `#8A6A22`, the same value as `gold-ink`, and it must not go lighter.** It was `#A07830` in all 18 places it appears, which puts white text at 4.02:1 — an AA failure Lighthouse never reported, because it does not evaluate hover states. Scoring 100 is a floor, not a proof.
- Animations use **Framer Motion** (`motion.*`, `useInView`, `useInView`). Server components that need scroll-triggered animations must add `"use client"`.
- **Google Analytics loads only for a visitor who accepted it, and the gate is "render nothing", not a flag.** `Analytics.tsx` returns `null` until the answer is `"granted"`, so a refusal leaves no script tag, no `window.gtag` and no request to Google — the tracker used to load for everybody the moment `NEXT_PUBLIC_GA_ID` was set, which it is on Production. The tempting alternative is Google's own consent mode (load always, declare denied), and it is **not** equivalent: it still fetches a third-party script and pings Google from a page the visitor has not agreed to be measured on. That choice is also what makes `track()` in `src/lib/analytics.ts` safe — it has no consent check of its own because there is no `gtag` to call, so a caller cannot track someone by forgetting to check. Do not load the script early and guard the call sites instead. The answer lives in `localStorage` under `pmafi:analytics-consent`, **versioned**: anything that is not an intact record at the current `CONSENT_VERSION` — malformed, hand-edited, written by an older build — reads as *no answer* and asks again, never as consent. Bump the version when what is being consented to changes, or an old yes to GA silently becomes a yes to whatever was added. React reads it through `useSyncExternalStore` (`ConsentProvider.tsx`), which is what keeps tabs in agreement and what stops the notice flashing at visitors who answered months ago: the **server snapshot is `undefined` (not read yet), never `null` (nobody answered)**, and collapsing those two puts the bar in the HTML for everyone. The notice has **no dismiss** — no close cross, no Escape — because dismissal is not an answer, and its two buttons are deliberately the same size and weight, since a grey Decline beside a bright Accept collects a yes by making the no harder to find. `CookieSettings` in the footer is what lets an answer be taken back. **No `/privacy` page exists**, and the notice therefore states what is actually set rather than linking to a policy; writing one would mean making retention and data-subject commitments on PMAFI's behalf that PMAFI has not made — it is on the blocked list, not an oversight.
- **Events carry counts, never who.** Three are wired (`member_id_downloaded`, `donation_form_opened`, `assistant_question_unanswered`) and none takes a parameter, deliberately: the ID page knows exactly which member is standing there, the donate page knows the gift, and the assistant box often holds a name or an address the visitor typed. `trackPageView` also sends the path **without its query string**, because `/donate/status` carries a donor's reference code — the thing the whole page is gated on. An event that would undo a gate elsewhere on the site does not get added just because it is easy to measure.
- The membership status check is a **server action** (`src/app/membership/actions.ts`) that reads a private Google Sheet via a service account. The full roster never reaches the browser — this is intentional and must not be changed.
- **The membership source of truth is the application form's linked RESPONSES sheet**, not a separate roster (`src/lib/members.ts`). Staff add a `Status` column; blank means Pending, because every row exists only because somebody applied — defaulting it to Lapsed would tell a new applicant their membership had expired. **Columns are located by header text, never by position**, since a responses sheet's layout belongs to the form and adding a question shifts everything after it. A row usually carries two email columns (the form's question plus the one Google adds because file upload forces sign-in) and a lookup matches either. Re-submissions collapse to one member with the best standing winning, so re-applying can never demote someone already Active. **The `Manual Members` tab wins outright — source beats standing** (`outranks`, decided 2026-09-19). That tab now holds the 7,747-row membership roll PMAFI supplied, with the standings PMAFI set; the form tab holds applications. When the roll and an application describe the same person, the roll is the Foundation's own record. This reversed a tie-break-only rule from earlier the same day, and it gives up one guarantee knowingly: a manual `Lapsed` can pull down a form `Active`. Unreachable while every row on the roll is Active, and the intended answer on the day one is not. Within a single tab nothing changed — best standing wins, newer row breaks a tie — so re-applying still cannot demote anybody. **Rows also merge on a shared name + PMA class, not only a shared address**, because the roll arrived with no emails and carries placeholder addresses, so a member who had also applied overlapped with their own application in nothing and answered `ambiguous` permanently. A *different* class still means a different person (37 names on the roll recur across classes), and an empty class never matches another empty one. `references/membership-autoadd.gs` and the roster generator are no longer used.
- **Members staff add by hand belong on the `Manual Members` tab, never in the responses sheet.** A Google Form writes each response to the row after the last one *it* wrote — a position it tracks itself, not the bottom of the sheet — so hand-typed rows sit in space the form still considers free and get overwritten one per submission, silently. The roster is the union of both tabs, read through the same header-based mapper. **A manual row mints a digital ID card exactly like a form row does.** It briefly did not — the argument being that staff typed both the name and the address, so nobody had shown the address belonged to the person named. PMAFI settled it on 2026-08-31: the address on a manual row is the member's own, asked for so the member can be reached, not invented for them. Roughly half the roster is manual, so refusing them locked out a large share of the membership for no gain the gate could actually deliver — it proves an address is *on* the roster, never that the visitor owns it, for form members too. `MemberRecord.source` is still populated and tested but decides no access; it records which tab a member came from, and a manual member who later submits the form is still promoted to `"form"` by group rather than by winning row, because the staff-set `Active` usually outranks the blank status a fresh submission carries.
- **A card can be minted from a NAME, and that is a decision rather than a drift.** `idByNameAction` issues a card from a name alone; it ran behind `DEMO_ID_BY_NAME` for a preview demo until **PMAFI settled on 2026-09-19 that this is the intended behaviour on the live site** — most of the roster cannot say which address the Foundation holds for them, and about half of it was typed in by staff, so leading with the email locked out exactly the members least able to guess it. The flag and `lib/demo-flags.ts` are **deleted rather than switched on**, because a flag nobody may turn off is not a flag, and an unconfigured environment is now the working case (pinned by a test). **What the decision accepts, and it is not small:** names are public — alumni lists, reunion programmes, this site's own `/about#board` page — so the card, which bears the Foundation's seal, is mintable and therefore forgeable by anyone who can read one; and because the card prints them, this hands out the **PMA class and joining year** that the `/membership` status check deliberately withholds. The mitigation is only that the card has always stamped `as of <date>`, making it a dated assertion rather than a standing credential. **Three guards predate the decision, were no part of it, and must not be relaxed alongside it:** an ambiguous name still gets the class-year follow-up and **never** a list of candidates; the action still **never returns an email**, since the card's number is derived from the member's stored address server-side (`src/lib/member-id.ts`) and only the number travels; and it is still rate-limited per client address, which is what bounds working through a list of plausible alumni names.
- **The two lookups stay separate functions, even now that both accept a name.** `checkMembershipAction` takes an email only; `idByNameAction` takes a name and serves `/membership/id`; `lookupMembershipAction` serves the `/membership` status check. They are not merged because they return **different things** and the difference is load-bearing: the status check **blanks the email** in its result (everything an action returns is serialized to the browser, so returning it would be name-to-email harvesting) and withholds the class year, while the ID path must return the class and joining year because the card prints them. Collapsing them would mean one function whose output depends on a caller-supplied mode — exactly the shape where the status check quietly acquires the ID path's disclosures. Both name paths are rate-limited per client address, since a name is guessable in a way an address is not, and both answer `ambiguous` rather than guessing.
- **`ambiguous` asks for a PMA class year; it must never list the candidates.** A shared name is resolved by a second field the visitor fills in — `findMemberByName(name, classYear)` narrows the tied matches and returns the one member in that class. Showing the near matches to pick from is the obvious UX and is permanently out of bounds: names are public and standings are not, so answering a guessed name with real members' names makes the status check a roster directory, which is the thing `members.ts` exists to prevent. Three rules keep the field from becoming its own leak, and all three are tested in `members-name.test.ts` — **a wrong year and an unhelpful one both return `ambiguous`**, never `none`, or the field reports which classes those members are *not* in; **a member with no class on file can never be narrowed to**, since an empty value must not match an empty query; and the year is a **tie-breaker only**, never a second gate, so an unambiguous name still resolves with a wrong year or none at all. The per-IP rate limit on `lookupMembershipAction` is what bounds guessing the year itself — it is a narrowing factor, not a secret, and the design accepts that.
- **The name match is forgiving, and the tier order is what keeps it safe.** `findMemberByName` tries, in order: exact-after-folding · word-set (`Cruz, Juan` == `Juan Cruz`) · spacing (`Delacruz` == `Dela Cruz`) · **containment in either direction**, so a member may omit a middle name the roster holds or supply one it doesn't · **spelling**, within two edits across the whole name. Middle initials and generational suffixes are dropped as non-distinguishing, since the same person is written all three ways across the form and the manual tab. The order matters: anyone who spells their name the way the roster holds it is matched by an earlier tier and can never be handed a near neighbour's record. The guards on the last tier are load-bearing and must not be loosened — **short words (≤3 letters) get zero leeway**, because one edit is the whole distance between Lim and Kim, Sy and Ty; **both names need at least two distinguishing words**, so a lone surname never resolves to whoever happens to be the only Cruz; and **only the closest members are returned, with a tie answered `ambiguous`** — a probe gets a shrug, never a correction. Because a spelling match can land on a real neighbour, `MembershipCheck.tsx` prints the matched name in full on the name path; the greeting alone is a first name, which would read as a typo rather than as the wrong person's standing.
- The **digital member ID generator** lives at `/membership/id` (`src/app/membership/id/`). **It is gated** — `IdGate.tsx` runs the membership check first and only renders `DigitalIdGenerator` on a roster hit. Name, category, standing, PMA class and member-since all come from the roster and are **not editable**; the photo is the only thing the visitor supplies. This is load-bearing: the card was previously built from whatever was typed, which made it a forgeable credential bearing the Foundation's seal. A lapsed member still gets a card — it says LAPSED. **The standing is stamped `as of <date>` beside the pill, and that must not be removed.** A PNG never changes while the membership it describes does, so a bare `ACTIVE` stops being true the day the roster moves and the card goes on asserting it; `ACTIVE as of 31 August 2026` stays true forever and tells whoever is shown a two-year-old card to check. **`MEMBER SINCE` is withheld and that slot prints `ISSUED` plus the generation date for everybody** (decided 2026-09-19). There is no "member since" question on the application form, so the year was derived from the row's `Timestamp` — the submission date on a form row, but on a `Manual Members` row whatever staff typed, unvalidated and often nothing. Roughly half the roster is manual, so the card asserted a joining year it had no basis for across a large share of it, and a blank one silently produced a differently *labelled* card rather than an obviously missing field. The slot already rendered `ISSUED` whenever the timestamp was missing, so this is that path made universal, not new drawing code. `MemberRecord.memberSince` is **still derived, still returned by both actions and still tested** — only the rendering is gone, which is what keeps it a one-line restore once the roster has a joining year that means something: a column staff fill in deliberately, not a timestamp reused for a second purpose. Do not restore it by pointing it back at the timestamp. The card is composited on a `<canvas>` and downloaded as a PNG; nothing is ever uploaded. The photo is cached in **`localStorage`** (`pmafi:id-photo`, downscaled) so a returning member need not re-upload — browser-local, never server-side, and there is a "Forget my photo" control. **No page may say the photo is "not stored".** Two FAQ answers did, and it was false — browser-local is a world away from uploaded but it is not nowhere, and the difference is exactly what matters to somebody who built their card on a shared computer. "Never uploaded" is true and stays sayable; `faq.test.ts` guards the stronger claim, alongside the QR-code and tax-deductibility guards. A member whose name is recorded wrongly cannot edit it — that is the point — so the page offers a **correction request form** instead, linked from the `form.correction` content key (`references/correction-form.gs`); a blank key hides the control rather than rendering a dead link, as `form.donation` does. Corrections are reviewed by staff and never written by the site: the service account is `spreadsheets.readonly`, and a web-facing credential that can edit the roster is a much larger risk than a form — do not "improve" this into a direct write. The member number is a deterministic FNV-1a hash of the **email**, not the name (`idFromEmail`, now in `src/lib/member-id.ts` so the server can derive it too) — the email is the roster's key, so fixing a typo in a name no longer reissues a different number. Known limitation: the gate confirms an email is *on* the roster, not that the visitor *owns* it — closing that needs real sign-in (Phase 3, Module A). Scan-to-verify is still unbuilt; it would need photos persisted (e.g. Vercel Blob) + an id-lookup endpoint.
- **The ID page asks for a current email and mobile number, and it asks by linking to a form.** `form.contact` (`references/contact-update-form.gs`) is the third form key beside `form.donation` and `form.correction`, and it exists for the same single reason all three do: **the service account is `spreadsheets.readonly` and must stay so.** The details go to PMAFI's own Google Form and land on a `Contact Updates` tab, which also keeps the collection PMAFI's rather than the website's — the same footing as the membership application, and it matters while the site still has no privacy policy. `/membership/id` is where it is asked because that is the one moment the Foundation knows it is looking at a real member doing something they came to do; about half the roster is manual rows that may carry no number at all, and a form member's number is as old as their application. **It asks, it does not gate** — the card downloads either way, since the ID is a benefit the roster already grants and nothing here can be verified anyway, so a member who would rather not give a number would simply type digits and the data would be worse rather than more. Note the site reads **neither** the phone nor the email column off the roster (only name, email, category, status, PMA class, timestamp are mapped), so this is for PMAFI's own correspondence and nothing on the site displays it.
- **Form links may be prefill templates, and every one must go through `applyPrefill`.** `form.contact` and `form.correction` each accept either a plain form URL or a Google prefill link carrying the literal token `PMAFI_EMAIL_HERE`; `src/lib/form-prefill.ts` swaps in the address the member already gave the gate. Prefilling matters because **staff match a response to a member by email** — it is the roster's key — and an address retyped from memory is the one that arrives wrong. Two rules: a plain link must keep working untouched (that is what staff paste if they skip the step), and **a URL with nothing to substitute must have the token stripped, not passed through** — the not-found branch and the demo name path both know no address, and rendering the raw template would put the literal text `PMAFI_EMAIL_HERE` in the form's email box for the member to delete. Both are tested in `form-prefill.test.ts`. The `.gs` generators are **creators, not editors**: re-running one mints a second form with a new link and strands the responses on the first, so a question added to a generator after the form was built has to be added to the live form by hand.
- **Two email addresses, and they are not interchangeable.** `PMAFI_PMA@yahoo.com` is PMAFI's official published address — it is what `contact.email` holds, what the site shows, and where users are told to write. `pmafi.web@gmail.com` is the **Google account that owns the Forms, the spreadsheets and the Apps Script**; a Yahoo address cannot own a Google Form, so every "sign in as…" instruction keeps it. Never replace one with the other in bulk. Phone number, social media URLs and real news items are **pending PMAFI confirmation** — do not invent or hardcode placeholder values. Confirmed 2026-08-17: membership fee ₱3,000 one-time lifetime for all categories and Metrobank account number `0223002800705`. **The payment gap is now closed**: the account name (`PMA Foundation Inc or PMAFI`) and a GCash channel (`Maribel Galano`, `09173270229`) followed, so `hasPaymentDetails()` is true and `/donate` and `/membership` both print the figures — copy that still tells a visitor to email for bank details is stale, not cautious. BIR donee status is *being updated*, which is not the same as held — **no page may claim tax-deductibility**.
- **The ₱3,000 fee supersedes the Annual Report, and that is settled — do not re-raise it.** `references/PMAFI ANNUAL REPORT book 2025` describes membership as qualifying by donation instead: at least ₱2,000 for Regular, ₱1,000 for Associate and Affiliate. That is the *2025* position; the flat ₱3,000 was confirmed by PMAFI on 2026-08-17 and is what `/membership` publishes. Reading the report and "correcting" the site back to tiered figures would undo a deliberate decision. Note the category copy on `/membership` describes eligibility by **who a member is** — alumni, faculty and staff versus outside individuals and organisations — never by amount, which is what keeps it compatible with a single fee.
- **PMAFI's photo drops are NOT a safe-by-default pool — read a frame before you publish it.** There are two gitignored client folders, and between them they contain material that must never reach `public/`. The clearest case is `AUDITOR IN ACTION.jpeg`: the ceremonial cheque on the wall behind the subjects is fully unredacted, showing a real BPI account number, account name (*PMA Class of 1971*), cheque number, MICR routing line, barcode and a signature. `/donate`'s handover photo is safe only because that cheque's account and routing digits are all-sevens dummies and its amount was destroyed at the pixel level — that is the standard any gift photograph has to meet. Others in the drops are personal social snapshots rather than Foundation business. **Every photograph published from these folders has been opened and looked at first**; a filename is not a description, and several of them are wrong about the year as well. Note also that most of the ~30 files are repeat frames of about eight occasions, so the pool is far smaller than the count suggests.
- **Redaction destroys pixels at source resolution, before the export crop — never an overlay, never just a tighter crop.** Two published photographs are redacted: `donation-handover.jpg` (amount, and its legible reflection in the glass table) and `gift-presentation.jpg` (a real personal cheque, plus a Metrobank slip with a MICR line and filled forms on the table). Both were flattened at full size and cropped afterwards, so nothing returns by disabling CSS or fetching a larger `_next/image` derivative. Feather the edges — a hard rectangle reads as a censor bar, a feathered one as foreground defocus — and **check the result by magnifying the shipped file**, not the source.
- **Photo captions on the site never name the people in them.** `/donate` set it ("the caption stays general rather than restating the name") and the home page's `AtWork` band follows it. These are posed photographs of official occasions in which serving officers are identifiable; a caption attaching names to faces turns an event photograph into a published record of a named individual, which is not PMAFI's to publish on their behalf. Dates are only used when legible **inside** the frame — the EXIF is stripped from every file PMAFI has sent, so there is no other trustworthy source, and a frame with nothing legible runs undated rather than plausibly dated.
- **The annual report is a reference, not a source of site copy, and must never be committed.** It carries the complete membership roster — several thousand names with class years — and this repository is public. Keeping the full roster out of the browser is the whole point of `src/lib/members.ts`; committing the PDF would undo that in one step. Facts drawn from it (SEC registration 1988, the 15-trustee board plus the Superintendent *ex officio*, PMA Road Map 2028, the faculty-doctorate plan) are already reflected in `/about` and `/programs` **in the site's own wording** — the deliberate verbatim passages are the attributed blockquote on `/programs` and the Vision and Mission on `/about`, and all three must stay word for word.
- **The Vision and Mission on `/about` are PMAFI's adopted statements, quoted exactly — never reword them.** They are sections 1.2 and 1.3 of the Foundation's governing document, supplied 2026-09-03, and they replaced copy that had been written on PMAFI's behalf. This is the one place where house style loses: `"assist the PMA improve"` reads as though a *to* is missing, and it stays, because a formally adopted statement is quoted or it is not quoted. Changing either needs PMAFI to amend the document first. `MissionValues.tsx` also has no headline above them any more — an invented headline over an official statement is the same problem in a smaller font.
