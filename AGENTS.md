# Project: PMAFI Website

**What this is:** The official website of the Philippine Military Academy Foundation, Inc. (PMAFI) — a non-stock, non-profit foundation supporting PMA.

**Live URL:** https://www.pmafi.org  
**Stack:** Next.js 16 · React 19 · Tailwind CSS v4 · Framer Motion 12 · TypeScript · shadcn/ui · Vercel

## Key facts for agents

- All pages are in `src/app/` using the App Router. Section components live in `src/components/sections/`, one subfolder per page.
- **Every dark page hero is `src/components/ui/PageHero.tsx`.** Do not hand-roll another one — this markup was copy-pasted across seven pages and drifted into a dozen blob sizes and two padding scales before it was extracted. Pass `eyebrow`, `title` (with the accent word in `<span className="text-gold-shimmer">`), `lede`, and optional `children` for a CTA. The home page's `sections/Hero.tsx` is deliberately separate — it is a full-viewport hero, not a page header.
- **Section vertical rhythm is a three-step scale: `py-16` (compact) · `py-20` (standard) · `py-24` (generous).** Nothing else. Reach for one of these rather than inventing a `py-28`. **The one exception is navbar clearance, which is not rhythm**: the navbar is `fixed` and transparent, so nothing in the layout reserves space for it and the top padding of a full-height hero is the only thing that keeps content out from under it. `Hero.tsx` carries `py-32` and `PageHero.tsx` `pt-28` for that reason alone, and both are sized against the bar (96px on mobile, 104px from `sm`) rather than against this scale. Anything that makes the bar taller — a larger seal, another line of brand text — has to be re-checked against both, on a short viewport where the hero content overflows rather than a desktop one where it never reaches the top.
- **`STATUS.md` is the source of truth for what is and isn't working** — pages, verified flows, configuration, open issues, and what is blocked on PMAFI. It is committed. `BUILD-STATUS.md` holds only engagement and payment matters and is **excluded from git** (`.git/info/exclude`) because this repository is public; never commit it. The scope docs (`PHASE-1/2/3-SCOPE.md`) describe what was sold, not what is live. `references/pmafi-information-request.md` lists everything still outstanding from the client.
- The **Board of Trustees** is a section of `/about` (`src/components/sections/about/BoardOfTrustees.tsx`), not its own page. Its `id="board"` anchor is load-bearing — nav, footer, programs page and the FAQ assistant all link to `/about#board`, and `/board` 308-redirects there via `next.config.ts`.
- **Fund names have one canonical list: `src/lib/funds.ts`.** The name is typed by hand into two separate sheets — the donation log's Fund column and the Fund Updates tab's — and `/donate/status` joins a donor's gift to their fund's updates by matching those strings, so both parsers read through `canonicalFund()`. The authority is the PMAFI brochure, which offers exactly two funds (Professorial Chair Fund, ₱250,000 minimum; Endowment Fund, ₱100,000); `General Fund` is ours for undesignated gifts. **"Facilities & Modernization" is a programme area, not a fund** — it appears on `/programs`, `Services.tsx` and `SupportImpact.tsx`, and adding it back to the fund list would advertise an offer PMAFI has never made. An unrecognised fund is passed through trimmed rather than dropped, so a fund opened later still works provided both sheets spell it identically. `references/donations-sheet.gs` mints references and must stay in step with this list.
- The **donor giving lookup** at `/donate/status` requires email **plus** a reference code, unlike the membership check which needs only an email. That asymmetry is deliberate: it exposes amounts rather than a standing. Every failed lookup must keep returning one identical message — distinguishing "no such reference" from "wrong email" would turn the page into an oracle for whether an address has ever donated.
- The site uses **Tailwind CSS v4** — the config is in `src/app/globals.css` (not `tailwind.config.js`). Custom animations (`animate-drift`, `animate-drift-slow`, `animate-ember`) are defined there.
- **Brand gold has two tokens** (defined in `globals.css` `@theme`): `text-gold` (`#C8A951`, vivid — use on dark/navy backgrounds) and `text-gold-ink` (`#8A6A22`, darker — use for small text on light/white backgrounds). The vivid gold fails WCAG AA contrast on light backgrounds, so always use `text-gold-ink` for gold text on white/slate sections. Likewise, muted helper text on light backgrounds must be `text-slate-500`+ (not `text-slate-400`, which fails AA). All public pages currently score 100 on Lighthouse accessibility — keep it that way. **The gold button's hover shade is `#8A6A22`, the same value as `gold-ink`, and it must not go lighter.** It was `#A07830` in all 18 places it appears, which puts white text at 4.02:1 — an AA failure Lighthouse never reported, because it does not evaluate hover states. Scoring 100 is a floor, not a proof.
- Animations use **Framer Motion** (`motion.*`, `useInView`, `useInView`). Server components that need scroll-triggered animations must add `"use client"`.
- The membership status check is a **server action** (`src/app/membership/actions.ts`) that reads a private Google Sheet via a service account. The full roster never reaches the browser — this is intentional and must not be changed.
- **The membership source of truth is the application form's linked RESPONSES sheet**, not a separate roster (`src/lib/members.ts`). Staff add a `Status` column; blank means Pending, because every row exists only because somebody applied — defaulting it to Lapsed would tell a new applicant their membership had expired. **Columns are located by header text, never by position**, since a responses sheet's layout belongs to the form and adding a question shifts everything after it. A row usually carries two email columns (the form's question plus the one Google adds because file upload forces sign-in) and a lookup matches either. Re-submissions collapse to one member with the best standing winning, so re-applying can never demote someone already Active. `references/membership-autoadd.gs` and the roster generator are no longer used.
- **Members staff add by hand belong on the `Manual Members` tab, never in the responses sheet.** A Google Form writes each response to the row after the last one *it* wrote — a position it tracks itself, not the bottom of the sheet — so hand-typed rows sit in space the form still considers free and get overwritten one per submission, silently. The roster is the union of both tabs, read through the same header-based mapper. **A manual row mints a digital ID card exactly like a form row does.** It briefly did not — the argument being that staff typed both the name and the address, so nobody had shown the address belonged to the person named. PMAFI settled it on 2026-08-31: the address on a manual row is the member's own, asked for so the member can be reached, not invented for them. Roughly half the roster is manual, so refusing them locked out a large share of the membership for no gain the gate could actually deliver — it proves an address is *on* the roster, never that the visitor owns it, for form members too. `MemberRecord.source` is still populated and tested but decides no access; it records which tab a member came from, and a manual member who later submits the form is still promoted to `"form"` by group rather than by winning row, because the staff-set `Active` usually outranks the blank status a fresh submission carries.
- **There are deliberately two membership lookups, and they must not be merged.** `checkMembershipAction` takes an email only and is what `/membership/id` calls to mint a card. `lookupMembershipAction` additionally accepts a **name** and serves only the `/membership` status check. Names are public — alumni lists, reunion programmes, this site's own board page — so allowing one to mint a sealed ID card would make the credential forgeable by anyone who can read. Keeping them as separate functions means the ID path has no name branch to reach, rather than a flag that could be flipped. The name path also **blanks the email** in its result (everything an action returns is serialized to the browser, so returning it would be name-to-email harvesting) and is rate-limited per client address, since a name is guessable in a way an address is not. A name matching two members returns `ambiguous` rather than guessing.
- **The name match is forgiving, and the tier order is what keeps it safe.** `findMemberByName` tries, in order: exact-after-folding · word-set (`Cruz, Juan` == `Juan Cruz`) · spacing (`Delacruz` == `Dela Cruz`) · **containment in either direction**, so a member may omit a middle name the roster holds or supply one it doesn't · **spelling**, within two edits across the whole name. Middle initials and generational suffixes are dropped as non-distinguishing, since the same person is written all three ways across the form and the manual tab. The order matters: anyone who spells their name the way the roster holds it is matched by an earlier tier and can never be handed a near neighbour's record. The guards on the last tier are load-bearing and must not be loosened — **short words (≤3 letters) get zero leeway**, because one edit is the whole distance between Lim and Kim, Sy and Ty; **both names need at least two distinguishing words**, so a lone surname never resolves to whoever happens to be the only Cruz; and **only the closest members are returned, with a tie answered `ambiguous`** — a probe gets a shrug, never a correction. Because a spelling match can land on a real neighbour, `MembershipCheck.tsx` prints the matched name in full on the name path; the greeting alone is a first name, which would read as a typo rather than as the wrong person's standing.
- The **digital member ID generator** lives at `/membership/id` (`src/app/membership/id/`). **It is gated** — `IdGate.tsx` runs the membership check first and only renders `DigitalIdGenerator` on a roster hit. Name, category, standing, PMA class and member-since all come from the roster and are **not editable**; the photo is the only thing the visitor supplies. This is load-bearing: the card was previously built from whatever was typed, which made it a forgeable credential bearing the Foundation's seal. A lapsed member still gets a card — it says LAPSED. **The standing is stamped `as of <date>` beside the pill, and that must not be removed.** A PNG never changes while the membership it describes does, so a bare `ACTIVE` stops being true the day the roster moves and the card goes on asserting it; `ACTIVE as of 31 August 2026` stays true forever and tells whoever is shown a two-year-old card to check. The card also prints both `MEMBER SINCE` and the generation date rather than dropping one for the other. The card is composited on a `<canvas>` and downloaded as a PNG; nothing is ever uploaded. The photo is cached in **`localStorage`** (`pmafi:id-photo`, downscaled) so a returning member need not re-upload — browser-local, never server-side, and there is a "Forget my photo" control. The member number is a deterministic FNV-1a hash of the **email**, not the name (`idFromEmail`) — the email is the roster's key, so fixing a typo in a name no longer reissues a different number. Known limitation: the gate confirms an email is *on* the roster, not that the visitor *owns* it — closing that needs real sign-in (Phase 3, Module A). Scan-to-verify is still unbuilt; it would need photos persisted (e.g. Vercel Blob) + an id-lookup endpoint.
- **Two email addresses, and they are not interchangeable.** `PMAFI_PMA@yahoo.com` is PMAFI's official published address — it is what `contact.email` holds, what the site shows, and where users are told to write. `pmafi.web@gmail.com` is the **Google account that owns the Forms, the spreadsheets and the Apps Script**; a Yahoo address cannot own a Google Form, so every "sign in as…" instruction keeps it. Never replace one with the other in bulk. Phone number, social media URLs, the bank account NAME, and real news items are **pending PMAFI confirmation** — do not invent or hardcode placeholder values. Confirmed 2026-08-17: membership fee ₱3,000 one-time lifetime for all categories, Metrobank account number `0223002800705` (account name still outstanding), and BIR donee status is *being updated*, which is not the same as held — **no page may claim tax-deductibility**.
- **The ₱3,000 fee supersedes the Annual Report, and that is settled — do not re-raise it.** `references/PMAFI ANNUAL REPORT book 2025` describes membership as qualifying by donation instead: at least ₱2,000 for Regular, ₱1,000 for Associate and Affiliate. That is the *2025* position; the flat ₱3,000 was confirmed by PMAFI on 2026-08-17 and is what `/membership` publishes. Reading the report and "correcting" the site back to tiered figures would undo a deliberate decision. Note the category copy on `/membership` describes eligibility by **who a member is** — alumni, faculty and staff versus outside individuals and organisations — never by amount, which is what keeps it compatible with a single fee.
- **PMAFI's photo drops are NOT a safe-by-default pool — read a frame before you publish it.** There are two gitignored client folders, and between them they contain material that must never reach `public/`. The clearest case is `AUDITOR IN ACTION.jpeg`: the ceremonial cheque on the wall behind the subjects is fully unredacted, showing a real BPI account number, account name (*PMA Class of 1971*), cheque number, MICR routing line, barcode and a signature. `/donate`'s handover photo is safe only because that cheque's account and routing digits are all-sevens dummies and its amount was destroyed at the pixel level — that is the standard any gift photograph has to meet. Others in the drops are personal social snapshots rather than Foundation business. **Every photograph published from these folders has been opened and looked at first**; a filename is not a description, and several of them are wrong about the year as well. Note also that most of the ~30 files are repeat frames of about eight occasions, so the pool is far smaller than the count suggests.
- **Redaction destroys pixels at source resolution, before the export crop — never an overlay, never just a tighter crop.** Two published photographs are redacted: `donation-handover.jpg` (amount, and its legible reflection in the glass table) and `gift-presentation.jpg` (a real personal cheque, plus a Metrobank slip with a MICR line and filled forms on the table). Both were flattened at full size and cropped afterwards, so nothing returns by disabling CSS or fetching a larger `_next/image` derivative. Feather the edges — a hard rectangle reads as a censor bar, a feathered one as foreground defocus — and **check the result by magnifying the shipped file**, not the source.
- **Photo captions on the site never name the people in them.** `/donate` set it ("the caption stays general rather than restating the name") and the home page's `AtWork` band follows it. These are posed photographs of official occasions in which serving officers are identifiable; a caption attaching names to faces turns an event photograph into a published record of a named individual, which is not PMAFI's to publish on their behalf. Dates are only used when legible **inside** the frame — the EXIF is stripped from every file PMAFI has sent, so there is no other trustworthy source, and a frame with nothing legible runs undated rather than plausibly dated.
- **The annual report is a reference, not a source of site copy, and must never be committed.** It carries the complete membership roster — several thousand names with class years — and this repository is public. Keeping the full roster out of the browser is the whole point of `src/lib/members.ts`; committing the PDF would undo that in one step. Facts drawn from it (SEC registration 1988, the 15-trustee board plus the Superintendent *ex officio*, PMA Road Map 2028, the faculty-doctorate plan) are already reflected in `/about` and `/programs` **in the site's own wording** — the one deliberate verbatim quotation is the blockquote on `/programs`, which is attributed and must stay word for word.
